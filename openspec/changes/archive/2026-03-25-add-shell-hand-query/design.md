## Context

目前 shell UI 已不再常駐顯示手牌區塊，玩家主要透過中間事件流理解局面，再用底部命令列輸入 `/discard` 等指令。現況下雖然 TUI state 已保有 `handWithIds()` 與 `drawn_tile_id`，但缺少一個可直接把這些資料轉成玩家可讀摘要的查詢入口，導致玩家在摸牌後仍得憑記憶或重新比對事件流做決策。

這個 change 主要發生在 TUI 端，且跨越 command registry、事件流產生邏輯、鍵盤 accelerator 與牌面格式化規則。Zig core 與 IPC 協議本身不需要新增欄位，因為目前資料已足以支撐需求；真正需要先固定的是：摘要由哪裡產生、如何分組排序、何時自動顯示，以及快捷鍵要如何與既有 shell 指令共存。

## Goals / Non-Goals

**Goals:**
- 提供 `/hand` 本地查詢命令，讓玩家可在不離開 shell 主畫面的前提下查看手牌摘要
- 讓手牌摘要依牌型分行顯示，並在萬、筒、條等各行內提供穩定排序，提升掃讀速度
- 將摸到的牌獨立顯示，並在玩家自摸後自動補一組手牌摘要，直接支援下一步出牌決策
- 讓快捷鍵與命令列共用同一條 command 流程，維持 command-first 心智模型
- 以 TDD 推進，優先補齊 unit test 覆蓋手牌格式化、命令執行與自動顯示邏輯

**Non-Goals:**
- 不恢復常駐手牌面板或舊的 table-oriented 手牌顯示
- 不修改 Zig core、UDS 協議或新增查詢型 IPC 訊息
- 不在這個 change 內處理事件流捲動、歷史搜尋或其他 shell 查詢命令的全面重構
- 不引入整合測試或端對端測試；本次以 unit test 為主

## Decisions

### 決定 1：`/hand` 是純本地查詢命令，輸出寫入事件流而不是新開 UI 區塊

**選擇**：`/hand` 由前端本地執行，不送任何 IPC。命令執行後會把手牌摘要追加到中間事件流，讓「查看手牌」與「查看局況」、「查看命令回饋」共享同一條時間線。

**理由**：這最符合既有 shell 方向，也避免重新引入一塊常駐手牌面板，破壞三段式畫面結構。

**替代方案**：加入可切換的手牌 panel 或 popup。這雖然直觀，但會讓 shell UI 再度回到多視窗／多模式切換，而不是把資訊查詢收斂成命令。

### 決定 2：手牌摘要由 TUI 既有 state 派生，沿用 canonical tile metadata 分組與排序

**選擇**：手牌摘要直接使用 `handWithIds()` 與 `drawn_tile_id` 為資料來源；分組順序固定為萬、筒、條、風、三元、四季、四君子，行內排序沿用既有 `CanonicalTile.sort_key`，不新增 schema 欄位。輸出層重用既有 `text-render` ASCII 牌面模板，而不是重新退回文字牌名。

**理由**：現有 tile catalog 已提供穩定排序資訊與完整牌面分類，而 TUI 也已經有牌面 ASCII 渲染能力。直接重用兩者，可讓 `/hand` 的視覺語言和專案其他牌面輸出保持一致，同時避免為了純顯示需求去改 Zig 協議。

**替代方案**：
- 由 Zig 直接推送已格式化的手牌字串：會把顯示語義綁進 core，增加 IPC 負擔
- 新增額外排序權重 schema：現況已有 `sort_key`，再加欄位會造成重複資訊

### 決定 3：多行摘要以「多筆事件」寫入事件流，而不是依賴單筆事件內的換行渲染

**選擇**：`/hand` 與自摸後自動顯示都會產出一組有順序的 event entries，例如第一行為「你的手牌」，後續每行各是一個牌型分類；`drawn_tile` 另成一行。

**理由**：現有 `EventLog` 本來就以一筆 entry 對應一行內容。延續這個模型可避免依賴 OpenTUI 對單筆 multiline text 的細節行為，也讓每一行都能自然參與事件流裁切與顏色處理。

**替代方案**：把整份手牌摘要塞成單一 entry 的多行字串。這需要額外確認文字元件換行、邊框高度與裁切規則，風險較高。

### 決定 4：自動顯示僅在「你摸到牌」後觸發，且保留 `/hand` 手動查詢作為權威入口

**選擇**：當 state diff 判定玩家 0 摸到新牌時，事件流除了既有的「你摸到 X」外，再自動追加一組手牌摘要。其他時機（初始化、其他玩家摸牌、一般 turn_changed）不自動顯示；玩家仍可隨時手動輸入 `/hand` 或使用快捷鍵重看。

**理由**：自摸後是最需要立刻比對手牌的時間點。把自動顯示限制在這一刻，可最大化幫助、最小化事件流噪音。

**替代方案**：
- 每次 state_update 都重印手牌：事件流會過於擁擠
- 完全不自動顯示：玩家每次摸牌後都得多做一次查詢，操作節奏較差

### 決定 5：快捷鍵預設使用 `Ctrl+o`，並保留 `/hand` 作為不依賴快捷鍵的主入口

**選擇**：新增一個預設 accelerator 映射到 `/hand`，並讓它經過同一套 command registry / execute path。預設鍵選 `Ctrl+o`，避免與既有 `Ctrl+h` `/help` 映射及常見 Backspace 語義衝突。

**理由**：玩家希望有快速查詢入口，但 terminal 對 `Ctrl+h` 的處理並不穩定。以 `/hand` 作為穩定主入口、`Ctrl+o` 作為加速器，可兼顧可用性與實作風險。

**替代方案**：
- 直接使用 `Ctrl+h`：語義直觀，但容易與 terminal/Backspace 行為衝突
- 不提供快捷鍵：可行，但不符合這次需求

### 決定 6：以 unit test 為唯一驗證主軸，採 formatter/command-first 的 TDD 切分

**選擇**：先補 formatter 單元測試，再補 `/hand` 命令執行測試，最後補自動顯示與快捷鍵映射測試；不在這次 change 引入 OpenTUI snapshot 或互動整合測試。

**理由**：這個功能大多是純資料整理與命令路由，天然適合單元測試。先固定輸出格式與觸發時機，可讓後續實作更穩定。

**替代方案**：直接從 UI 渲染層做整合測試。這會提高測試成本，也不利於快速鎖定排序與格式細節。

## Risks / Trade-offs

- [事件流可能因自動顯示手牌而變得擁擠] → 僅在玩家自摸時自動追加，且空分類不輸出
- [不同 terminal 對 `Ctrl+o` 支援仍可能有差異] → 保留 `/hand` 作為主要入口，快捷鍵僅是加速器
- [排序邏輯若分散在命令與 state diff 兩處，未來容易飄移] → 抽成單一 hand summary formatter 供 `/hand` 與自動顯示共用
- [ASCII 牌面若與既有 tile template 能力脫節，花牌或字牌可能顯示異常] → 直接重用既有 `text-render` 路徑，必要時一併補齊花牌模板
- [以事件流逐行寫入時，手牌摘要可能被其他訊息切開] → 將整組摘要在同一個命令/狀態處理流程中同步追加，避免被非同步訊息插隊
- [只做 unit test 可能漏掉實際鍵盤事件整合問題] → 先以 command handler 與 formatter 鎖定核心邏輯；若實作後出現終端相容性問題，再補更高層測試

## Migration Plan

1. 在 command registry 中加入 `/hand`，先以 unit test 固定命令解析與 help 輸出
2. 新增 hand summary formatter，固定分組順序、行內排序與 drawn tile 分離規則
3. 將 `/hand` 命令接到 formatter，讓事件流可手動顯示手牌摘要
4. 在 state update 的自摸分支重用同一 formatter，自動追加手牌摘要
5. 補上快捷鍵映射與對應 unit test，確認其仍走命令層
