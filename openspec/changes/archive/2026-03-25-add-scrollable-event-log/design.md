## Context

目前 shell 主畫面的中間區域由 `EventLog` 直接渲染最近 18 筆事件，超出的內容會先在前端被裁掉，因此即使 state 內仍保有完整事件陣列，玩家也無法回看更早的訊息。這在 `/hand` 會一次追加多行摘要的情境下特別明顯，因為同一次輸出就可能超過可視高度，導致摘要上半部立刻消失。

這個 change 橫跨畫面容器、鍵盤互動與本地 UI state。它不需要變更 Zig core 或 IPC，因為事件資料本來就已經在前端；真正要先定清楚的是：事件流要如何捲動、何時自動跟隨最新訊息、以及在底部命令列長駐可輸入的前提下，哪些按鍵負責控制事件流。

## Goals / Non-Goals

**Goals:**
- 讓中間事件流成為真正可回溯的捲動視窗，而不是固定只顯示最後幾筆。
- 保持底部命令列作為主要輸入入口，不要求玩家先切換到另一種模式才能輸入指令。
- 為事件流捲動定義穩定且不易與現有快捷鍵衝突的鍵盤操作。
- 定義新事件到來時的自動跟隨規則，避免玩家回看歷史時畫面被強制拉回底部。

**Non-Goals:**
- 不在這個 change 內加入滑鼠捲輪、搜尋歷史、事件過濾或事件高亮。
- 不改動事件內容格式，手牌摘要仍維持逐行 event entry 的模型。
- 不引入新的 Zig 訊息欄位、IPC 命令或後端持久化機制。

## Decisions

### 決定 1：事件流改用 OpenTUI `scrollbox`，不再於渲染前做固定筆數裁切

**選擇**：中間視窗改為使用可捲動容器承載完整 event entries，移除目前 `slice(-18)` 這種先裁資料再渲染的做法。

**理由**：目前最大的問題不是資料不存在，而是資料在畫面層被直接丟棄。只要保留完整 entries 並交給 `scrollbox` 管理可視區域，就能自然支援回看較早訊息，也符合既有 spec 對可回溯事件流的描述。

**替代方案**：繼續沿用普通 `box`，但手動維護一個可視區間切片。這雖然可行，但要自行處理頁高、邊界、捲動步進與自動跟隨，複雜度高且容易與 OpenTUI 內建能力重疊。

### 決定 2：事件流維持「命令列常駐輸入」，捲動採用不需切焦點的全域導覽鍵

**選擇**：底部命令列保持主要焦點與輸入入口；事件流捲動使用 `PageUp`、`PageDown`、`Home`、`End` 這類不會干擾一般文字輸入的導覽鍵，不要求玩家先把焦點切到事件流。

**理由**：這個產品的核心是 command-first shell。若為了捲動而引入明顯的焦點切換模式，會讓玩家需要在「輸入命令」與「操作面板」之間切換心智模型。使用導覽鍵可保留 shell 操作節奏，也較不會與既有 `Ctrl+o`、`Ctrl+s` 等 accelerator 衝突。

**替代方案**：
- 讓事件流必須先取得 focus，再用上下鍵捲動：互動成本較高，且容易與命令列輸入衝突。
- 提供 `/scroll up` 這類 slash 指令：雖然非常 command-first，但對單純回看歷史過於笨重，操作節奏不自然。

### 決定 3：事件流採用「置底跟隨 / 手動脫離跟隨」雙狀態

**選擇**：當事件流位於最底部時，新訊息到來自動跟隨到底；當玩家手動往上捲動後，視窗進入脫離跟隨狀態，新訊息只追加內容，不強制把視窗拉回底部；按 `End` 可立即回到底部並重新進入跟隨狀態。

**理由**：玩家在正常對局中通常想看最新訊息，但在回看 `/hand` 或較早事件時，又不希望每次新訊息都打斷閱讀。雙狀態模型能兼顧即時性與可回看性。

**替代方案**：
- 永遠跟隨最新訊息：回看歷史體驗很差。
- 永遠不自動跟隨：每次有新訊息都要再手動回到底部，日常操作太重。

### 決定 4：捲動狀態維持在 TUI 本地，不進入 Zig game state

**選擇**：事件流目前位置、是否跟隨最新訊息等資訊只存在前端 UI 層，與 `eventLog` 同步使用，但不進入 Zig snapshot 或 IPC。

**理由**：這些資訊是純顯示狀態，和遊戲規則無關，也不需要跨客戶端同步。將其保留在前端可以避免污染 game state schema。

**替代方案**：把捲動位置序列化進 game state。這會把本地 viewport 細節錯誤地提升成跨邊界協定，沒有必要。

## Risks / Trade-offs

- [事件流與命令列同時監聽鍵盤，可能出現快捷鍵衝突] → 限定使用 `PageUp`、`PageDown`、`Home`、`End` 等導覽鍵，避免與常見 slash 輸入和既有 accelerator 重疊。
- [長時間對局後 event log 累積過多，捲動容器可能需要處理較多節點] → 先沿用既有完整事件陣列；若效能成為問題，再另開 change 討論虛擬化或歷史裁切策略。
- [OpenTUI `scrollbox` 的鍵盤預設與現有 shell 操作不完全一致] → 以本專案的鍵盤層統一定義捲動鍵與跟隨規則，不直接把互動語意交給元件預設行為。
- [新訊息到來時的跟隨判定若不穩定，會造成閱讀跳動] → 明確以「是否位於底部 / 是否手動脫離」作為狀態邊界，並在 spec 中寫成可測試情境。

## Migration Plan

- 這是純前端本地 UI 改動，無需資料遷移或協定版本切換。
- rollout 時直接以新事件流容器取代舊裁切邏輯即可。
- 若實作後發現捲動互動不理想，可暫時保留完整 event log 並退回單純顯示末端，但不需回滾任何 Zig 或 IPC 變更。

## Open Questions

- 是否需要在事件流脫離跟隨狀態時顯示明確提示，例如「已停留在歷史訊息」？
- PageUp/PageDown 應以固定行數還是一整頁高度為單位捲動，哪個更符合 OpenTUI 元件實際手感？
